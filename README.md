# Генератор карточек товаров для КИП (B2B)

Прототип на Python + Groq: по данным о приборе (JSON, веб-форма или **ссылка на страницу товара**) формирует черновик карточки для контент-менеджера:
SEO-заголовок (≤70 симв.), SEO-описание (800–1200 симв.), таблица характеристик, 3–5 поисковых запросов, commercial-блок («кому подходит / какие задачи решает») и список недостающих данных.

Главный принцип: **модель не может выдумать технические характеристики** — это обеспечено архитектурой, а не только промптом (см. ниже).

## Быстрый старт (Python 3.11+)

```bash
python -m venv .venv && source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env                                    # впишите GROQ_API_KEY
python -m card_generator --serve                        # веб-интерфейс: http://127.0.0.1:8000
```

Командная строка:

```bash
python -m card_generator examples/product_1.json examples/product_2.json   # → output/*.md, *.json
python -m card_generator --url https://…/страница-товара                              # из ссылки
python -m card_generator --dry-run examples/*.json                                    # только анализ пробелов, без LLM
python -m card_generator --list-models                                                # модели, доступные ключу
pytest                                                                                # тесты (без сети)
```

Docker: `docker build -t cards . && docker run --env-file .env -p 8000:8000 cards`

Ключ читается из переменной окружения или `.env` (в `.gitignore`). Модель по умолчанию `openai/gpt-oss-120b`, меняется через `GROQ_MODEL`.

## Архитектура

```
JSON / форма ─┐
              ├─► нормализация и проверка (product.py) ─► LLM (Groq, JSON-схема) ─► проверки (checks.py)
ссылка ───────┘                                              ▲                          │ не прошли?
 └ fetch (защита от SSRF) → текст → LLM-извлечение → дословная верификация             └─ повтор с списком ошибок (≤3)
                                                  │
 характеристики и «данных нет» — собирает КОД ─────┴──────────────► карточка (MD / JSON / веб)
```

## Защита от выдумок (слои)

1. **Характеристики не проходят через LLM.** Таблица строится кодом из `specs`; недостающие группы (диапазон, точность, питание, корпус/присоединение, интерфейсы) получают пометку «данных нет».
2. **Промпт**: роль, запрет фактов вне `<product>`, запрет чисел и юридически значимых утверждений без опоры, правило «лучше пробел, чем выдумка», входные данные объявлены данными, а не инструкциями (защита от prompt injection из паспортов и страниц).
3. **Программная проверка**: каждое число в сгенерированном тексте должно встречаться во входных данных; слова-маркеры выдумок (ГОСТ, сертификат, гарантия, взрывозащита, поверка…) допустимы только если есть во входных данных; длины заголовка и описания. При нарушении модель получает конкретный список ошибок и повторяет; если не получилось — карточка помечается «требует проверки человеком».
4. **Верификация извлечения по ссылке**: LLM достаёт поля из страницы, но любое значение, которого нет в тексте страницы дословно, отбрасывается и показывается пользователю.

## Другие решения

- **Groq**: сначала строгий `json_schema` (constrained decoding), при отказе модели — автопереключение на `json_object`; в любом случае ответ валидируется pydantic. Ретраи 429/5xx — на уровне SDK.
- **Обработка входа**: битый JSON, не-объект, пустой `name`, пустые/отсутствующие поля, нечитаемый файл — понятные сообщения без трейсбеков. Пробелы определяет код, модель только дополняет.
- **Безопасность загрузки по ссылке**: только http(s), только публичные IP (проверяется каждый редирект), лимит размера, таймауты. В веб-UI весь вывод рендерится как текст (без XSS).
- **Веб-UI** без сборки: копирование по блокам, счётчики длины, подсветка «данных нет», выгрузка Markdown/JSON.

## Ограничения и дальнейшие улучшения

- Проверка слов — по списку основ; тонкие выдумки (например, отрасль применения) она не ловит. Улучшение: второй LLM-проход «каждое утверждение подтверждено данными?» с цитатой-источником.
- Единый список «ожидаемых характеристик» для всех приборов (у манометра «питание» — шум). Улучшение: профили по категориям каталога.
- Страницы, которые строятся JavaScript-ом, и PDF-паспорта пока не читаются (нужен headless-браузер / PDF-парсер).
- SEO-запросы строятся по тексту, без реальной частотности (нужна интеграция с Вордстатом / Search Console).
- Нет очереди и кэша; для потока товаров — пакетный режим и кэш по хэшу входных данных.
- Для товаров с очень большим числом характеристик модель может превысить 1200 символов в описании; тогда карточка помечается «требует проверки человеком». Улучшение: выбор 4–6 главных характеристик перед генерацией и больше попыток с обратной связью.
## Примеры данных

`examples/product_1.json` (гигрометр ВИТ-2) и `examples/product_2.json` (термопреобразователь ОВЕН ДТС035) собраны с карточек товаров на souz-pribor.ru: значения характеристик перенесены как на странице, описание — по тексту страницы. У ВИТ-2 на странице не указан производитель, поэтому поле пустое, и сервис помечает его как «данных нет». `examples/product_3_incomplete_demo.json` — учебный пример с неполными данными для проверки обработки пробелов.
